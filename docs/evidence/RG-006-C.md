# RG-006 runtime ownership evidence

Source contracts are PRD 8, SRD 5 and the clarified HLD 5 / LLD 6 A-03. PR #18 targets the integration feature.

## Component behavior

RuntimeOwner owns one deployment-configured canonical runtime root across epoch directories. New initialization requires a new private directory and nonzero domain ID. Its immutable anchor binds schema, domain and canonical root path with SHA-256. Existing acquisition validates the anchor and enters RecoveryRequired; it cannot issue an initial claim or restore serving state.

A Fresh owner issues one move-only InitialEpochClaim. It is never reissued after use or token destruction. The claim binds domain/epoch, retains the shared root lock and supplies validated CLOEXEC root-directory duplicates for durable bootstrap storage. A second claim returns AlreadyUsed or transient Busy, preserving the legitimate token.

Owner PID, root/parent path identity, lock identity and anchor identity/content are checked. Ownership-validation failure irreversibly taints the owner and all shared claims. Forked use is rejected before mutex access. The anchor parser is bounded before DOM construction, and file opens reject FIFO/symlink substitutions. Canonical anchor bytes have a 4 MiB limit and root paths have a 4096-byte bound; these are internal implementation limits.

## Review dispositions

Root review required sticky invalidation, source-identity checks, nonblocking file opens, bounded anchor parsing, realpath RAII, and a fresh directory open-file description for enumeration. Fresh-claim issuance uses a short logical reservation; filesystem work runs outside the claim mutex. Reclaim checks occur before empty-root scanning so a legitimate epoch child never poisons the first token. Shared descriptor and read/write helpers were extracted from ManifestStore without changing its intended behavior.

The HLD/LLD startup clarification records stopped-container intents before OS start, then non-serving bootstrap and durable observed process identity before activation. PRD/SRD behavior and release gates are unchanged.

## Verification scope

Senior developer and Tester supplied separate always-on NDEBUG fixtures. Root performed strict local C++20 syntax checks. Local executable/sanitizer checks used test-only EVP shims and are excluded from real cryptographic acceptance. Linux CI must execute the real OpenSSL build.

Required evidence includes same-root lock contention, different-root scope, token-retained lock, existing-root recovery-only behavior, missing/replaced root/lock/anchor, domain/path checks, sticky failure after restoration, inherited PID rejection, initialization/crash boundaries, FIFO rejection and concurrent one-use claim issuance.

## Remaining work

Ownership is global only within the deployment's one trusted configured runtime root. Misconfigured alternate roots are outside that exclusion guarantee. Initial claims authorize bootstrap storage, not process launch, activation or proof of fencing.

A verified-fencing successor-epoch claim under the same root is not implemented. Recreating the root is not a recovery procedure. Actual Docker/OS control, authenticated bootstrap acknowledgement, positive cessation of all prior participants, no-restart enforcement, witness/trust readiness and serving activation remain RG-006 integration gates.
