# RG-006 bootstrap recovery reader evidence

**Scope:** PR #20, component RG-006-E. Sources: PRD 8 / SRD 5, HLD 5 and LLD 8 §21; [reader contract v1](../contracts/bootstrap-recovery-v1.md). Full RG-006 remains In progress.

## Implemented component

BootstrapRecoveryReader accepts validated recovery-mode RuntimeOwner ownership and reads existing bootstrap intents without changing them. It returns immutable diagnostic inventories, canonical digests, bounded file/directory identity observations and typed issues. Pending process identities and historical boot/clock provenance remain visible. A structurally complete scan is not past durability, process-exit, serving, reset or successor-epoch proof.

Initial mode/ownership/descriptor failures return typed fatal outcomes; later uncertainty returns an incomplete diagnostic snapshot where allocation permits. Unknown/missing/temporary/invalid artifacts, detected mutation, identity collisions, latched recovery or any resource/truncation condition prevent a complete scan. Safely decoded known records remain available when other records are uncertain.

The reader uses fresh directory open-file descriptions, sorted entry comparisons, RAII descriptors, no-follow/nonblocking opens, private-mode/single-link checks, bounded canonical decoding, owner/domain/epoch binding and repeated UID/link/mode/size/time/inode checks. It revalidates root ownership and metadata after scanning. This is detected-change evidence, not an atomic filesystem snapshot, authentication or rollback freshness.

## Resource and failure review

Fixed reader-only limits are 1,024 epoch directories, 4,096 all root entries, 16 all child entries, 64 MiB conservatively reserved attempted input, 16,384 retained participants, 256 global issues and 16 issues per epoch. Each intent retains the 4 MiB codec cap. Failed reads/decodes do not refund the input budget. Issue saturation flags truncation while allowing a safe known intent to be read within remaining work budgets. No cap authorizes reset.

Root review required exception-safe directory ownership, correct fdopendir failure cleanup, fresh enumeration offsets, hard issue caps even during final error reporting, sorted listings, preservation of valid siblings, full metadata comparisons and conservative byte charging. The independent audit corrected misleading LLD arrows and clarified pre-scan fatal versus post-scan incomplete ownership failure.

## Verification

Separate developer and independent tester suites use always-on checks under NDEBUG. Cases cover pending/complete/empty inventories, repeated read-only scans, unknown/temporary/missing/corrupt/binding-mismatched artifacts, FIFO/symlink/hard-link rejection, cross-epoch collisions, replacement/mode/root mutation, every injection hook and each finite limit. A truncated root enumeration is not required to contain a particular directory because filesystem enumeration order varies.

The developer's wrong-mode/read-failure fixture initially reused an already-created root. Linux run 45292023290 passed the independent suite and 49 of 50 total groups but correctly rejected reinitialization in that fixture. Root separated its temporary roots without relaxing ownership checks or deleting/recreating a recovery root. That failed run is excluded from acceptance.

Tester also executed the corrected developer suite under local ASan/UBSan. All local EVP-shim runs are fixture/behavior smoke only and excluded from cryptographic or Linux durability acceptance.

Linux [run 45292546023](https://github.com/kshiteesh28/DistributedRateGuard/actions/runs/45292546023) passed source `87c784b25d47dd97527709756fd63673671af470`, tested as merge ref `0784213de9ec24bf7e111224363f04a56909f4cb` against feature `cb98d7851fdac6f4eedab0d5f55a88a7fd98a798`: 50 CTest groups in each of two clean builds, 17 Python tests and 12 matching generated files. Real pinned OpenSSL sanitizer checks passed: six bootstrap/reader, three manifest, two runtime-owner, two lifecycle, three clock, eight history and twelve security groups. No sanitizer errors were reported. Subsequent evidence/design/tracking changes are documentation only. These are component results, not recovery fencing, deployment or numerical release-gate acceptance.

## Remaining integration

The reader does not launch, inspect, stop or fence processes; restore a store; acknowledge activation; or issue any epoch capability. EpochSupervisor must still reconcile the full artifact/runtime inventory, use a real controller to positively confirm cessation, satisfy all policy/trust/clock/witness gates and obtain a verified successor authorization. Unknown or untrusted inventory blocks reset. Artifact layout/controller integration, authenticated participant activation, witness and full lifecycle acceptance remain open.
