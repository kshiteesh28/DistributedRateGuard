# RG-006 bootstrap intent and identity evidence

Source contracts: PRD 8, SRD 5, HLD 5 and LLD 7 A-03/§21. PR #19 targets the integration feature and depends on PR #18's runtime ownership.

## Component contract

`BootstrapInventory` is an immutable value model. A revision-1 plan binds domain, epoch, authority incarnation, policy digest, expected common clock provenance and an exact roster of stopped-container intents. Initial process identities are explicitly absent; a zero PID is never exit evidence. Identity observations must match the planned role, slot, participant, incarnation and container, with nonzero PID/start and matching boot/time-namespace/clock identity.

Exact duplicate observations are idempotent. Unknown, changed or colliding identities produce a recovery-required successor value; recovery is irreversible. Revisions never wrap. The model supports arbitrary uint32 slot IDs and the existing maximum of eight replica entries, rather than restricting slot numbers to 1–8.

`BootstrapStore` consumes one move-only initial-epoch claim on success or failure. It creates a new private `epoch-<32 lowercase hex digits>` child beneath the validated runtime root. An existing child is never reused. A complete canonical `intent.json` is persisted before the caller may act on the plan. Each observed identity is a revision/digest CAS update and must be fully durable before an identity acknowledgement or subsequent launch action.

The store does not observe or start containers itself. Inputs are trusted controller observations, not proof generated by this library. `ReadyCandidate()` returns candidate data only after complete, matching identity registration and ownership/on-disk validation. It is not a serving permission.

## Publication and concurrency

Canonical schema-1 JSON uses decimal-string uint64 values, bounded duplicate/unknown-key rejection and SHA-256. The 4 MiB artifact cap is an internal limit. Digests detect corruption; they do not authenticate a writer or establish rollback freshness.

Initial publication uses POSIX no-replace `linkat`, then removes the temporary link and syncs the child directory. Updates sync a private temporary file, revalidate the current bytes and inode, atomically rename, sync the directory and read back. File opens reject symlinks, FIFOs, hard-link substitutions and invalid ownership/modes. Runtime-root ownership covers cooperative participants under the one trusted configured root; it does not protect against a malicious same-UID concurrent writer.

Results distinguish `NotVisible`, `Durable` and `VisibleDurabilityUnknown`. Publication visibility, storage error and model-transition status are separate fields. A durably persisted recovery-required transition still blocks readiness. After uncertain storage, the store remains unready and its snapshot remains the last fully durable in-memory value; disk may be ahead. Bounded orphan temporary files require recovery diagnosis, never automatic reuse.

A short mutex reserves one mutation/readiness operation; filesystem work runs outside it. Competing operations return Busy, stale CAS returns Conflict without poisoning a healthy store, and Snapshot returns an immutable shared value without filesystem I/O. No existing-store serving reopen or fenced successor claim is provided.

## Verification and review

Developer and Tester fixtures are separate, always-on under NDEBUG. They cover immutable transitions, canonical golden digests, malformed/tampered envelopes, independent clock/process collisions, exact duplicates, revision exhaustion, consumed claims, CAS conflicts, file tampering and replacement, pre/post-publication failures, crash boundaries, concurrent Busy and snapshot behavior, and readiness rejection after recovery or storage uncertainty.

Root review corrected allocation/exception boundaries, revision exhaustion, explicit success versus error fields and pre-publication allocations. Senior review identified revalidation between temporary-file sync and replacement; the update path now checks immediately before publication. Initial publication also uses no-replace semantics. Linux exposed an invalid race-test setup that pre-created the epoch directory before the injection point; that fixture was corrected while preserving the separate pre-existing-child test.

Local syntax and shim-linked smoke runs are not real cryptographic acceptance. It passed 48 CTest groups in each of two clean builds, 17 Python tests and reproduction of 12 generated files. Sanitizer suites passed: four bootstrap, three manifest, two runtime-owner, two lifecycle, three clock, eight history and twelve security groups, all with real pinned OpenSSL. Retained CI artifacts include clean-build and sanitizer logs. The following evidence/design/tracking delta is documentation only; no end-to-end release metric is claimed.

## Remaining integration

The EpochSupervisor-owned existing-intent recovery reader is also unimplemented; RuntimeOwner::OpenExisting does not read or restore a BootstrapStore. Actual stopped-container creation, Docker/OS process control, independently observed host process identity, authenticated bootstrap acknowledgements, policy/trust/witness gates and participant activation remain unimplemented. Existing roots remain RecoveryRequired. Positive termination of every old participant and a verified successor-epoch claim under the same root remain required; deleting or recreating the runtime root is not recovery. Full RG-006 acceptance remains open.
